Part VI · Reference & craft · Chapter 17

Development

The repository's own rules, and the three extension points that matter: a tool, a hook, a provider. Plus the shape of a change — because this codebase cares as much about how a diff reads as about what it does.

17.1The workspace

CommandWhat it must do
cargo buildCompile the binary (--bin wcode for just the CLI).
cargo test --workspacePass. Every change.
cargo clippy --workspace --all-targetsBe clean — not "mostly clean".
cargo install --path crates/wcode-cliInstall the current tree as wcode.
`cargo build` proves nothing about behaviour

The repository's guideline is explicit: prefer a live end-to-end check over unit tests alone. Point at a keyless local endpoint for the happy path, and at a refused port for the error path. A green build is a precondition, not evidence.

17.2The house rules

One logical change per commit

Imperative subject, area prefix: harness:, cli:, tui:, docs:. Example: cli: fence [workflow] to --task.

No anyhow

Errors are typed (thiserror) or plain strings at a boundary. A workspace-wide grep for anyhow returns nothing, and that is deliberate.

The kernel stays presentation-free

wcode-harness may not know what a terminal, a TOML file, or a team is. If a change needs that knowledge, it belongs in wcode-cli or a client.

Cite code as file:line + a snippet

The number locates, the quote pins it. Comments and docs in this repository are full of these anchors, which is why a reformat does not falsify them.

Track multi-step work

docs/next-steps.md is the index; a larger effort gets its own docs/*-plan.md; a decision gets docs/decisions/DNNN-*.md.

Absence is a design position

Before adding a config key, ask whether a Hooks impl would do. Before adding a dependency, ask what it replaces.

17.3Add a tool

Three steps: implement TypedTool, erase it, register it.

  1. Implement the trait crates/wcode-cli/src/tools/<name>.rs Typed args + schemars schema. Tool descriptions and field doc-comments are the interface — they are what the model reads.
  2. Register it tools/mod.rs default_tools() erased(MyTool). Mutating tools take the shared lock. A conditional tool hides behind a capability check (a binary on PATH) so the model never holds an unusable tool.
  3. Test behaviour, not shape #[cfg(test)] in the file Every tool in this repo has tests that would fail if the logic were wrong: a no-match, an ambiguous match, a refused argument, a cancellation.
Tool output is three fields, and two are for humans

output is what the model reads. diff and path are presentation-only — they ride the event to the UI and never enter the model's context, so showing a diff costs no tokens.

17.4Add a policy

Implement Hooks and push it into the set. Order matters, and the CLI pins it explicitly: safety first, token-saving second, situational policies after the worker template is cloned (so workers do not inherit root-only gates).

Two real examples from this repository show the two shapes a policy takes:

PolicyHook usedEffect
PlanModeHooksbefore_tool_callRefuses four editing tools and mutating shell commands while a shared flag is on.
VerifyGateHooksbefore_tool_callRefuses task{op:"complete"} for a work node no gate consumes.
ReportBackafter_runDelivers a worker's final message to its owner as a Wake.
SleepRefusalHooksbefore_tool_callRefuses a sleep-leading command (root only), so the model ends its turn instead of polling.

A policy that needs shared state (a plan, a flag, a registry) simply holds a clone of it — the handles are Arc-backed, which is why VerifyGateHooks can live in the CLI without the kernel depending on TaskList.

17.5Add a provider

A provider is one function: context, system prompt, tool definitions, options → a stream of events. rig_stream_fn() is the shipped OpenAI-compatible adapter; a new one is a new StreamFn, not a new loop.

Keep the loop's expectations: emit text deltas, thinking, tool calls, and a terminal signal; honour the cancel token; let the adapter own retries and stall timeouts. A fake StreamFn is also the cheapest way to test the loop — no network, no key.

17.6Documentation as part of the change

ArtifactWhen
docs/next-steps.mdThe tracker. Every multi-step effort has a row here, with a pointer.
docs/<topic>-plan.mdA larger effort: design, phases, decisions, open questions.
docs/decisions/DNNN-<slug>.mdOne decision worth remembering, with the alternatives weighed. The format is short: context, decision, consequences, amendments.
docs/work/WNNN-<slug>.mdA work item: ask, scope/non-scope, plan with gates, quality commands, expected outcome.
Why this book cites decisions

Because half of wcode's behaviour looks arbitrary until you read the record: why a workflow needs a task, why a gate is not a verification, why the default palette has no colour. The appendix indexes all 34.

17.7A change, end to end

  1. Recon — read the code the change touches; collect file:line evidence.
  2. Brief — for anything non-trivial: scope, non-scope, interface, numbered plan with a gate per step.
  3. Sketch — the interface first, as a reviewable block: signatures, types, contracts, test skeletons.
  4. Review the sketch — against the locked design, before any implementation exists.
  5. Implement — one logical change, tests that assert behaviour, clippy clean.
  6. Verify — a second read of the diff against the task, plus a live check where possible.
  7. Record — the work item's outcome and, if a decision was made, a DNNN file.

This is the loop the shipped workflow template encodes: explore → sketch → review-sketch → implement → verify → publish → ci. The template is not ceremony; it is this chapter, executable.
