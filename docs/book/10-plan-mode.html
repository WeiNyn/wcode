Part III · Inside · Chapter 10

Plan mode

A live toggle that tells the model "explore and propose, do not mutate" — and enforces it twice: by refusing the editing tools outright, and by scanning shell commands for obvious mutators. It is a guardrail with an honest boundary, and the boundary is documented.

10.1Three parts, one boolean

Plan mode is not a mode in the kernel's loop. It is the conjunction of three things, all driven by one shared atomic flag:

A shared handle

PlanModeHandle — a cloneable Arc<AtomicBool>, off by default, read by the hook on every tool call and written by the toggle.

A hook

PlanModeHooks implements before_tool_call: a Some(reason) blocks the call and feeds the reason back to the model.

A prompt section

PLAN_SECTION is appended to the system prompt while the flag is on, so the model knows the intent, not just the refusals.

That list is the whole tool half of the policy — four names. Everything else stays available on purpose: the agent must still be able to read, search, fetch, and record the plan as a todo list, or plan mode would be indistinguishable from "do nothing".

10.2The shell half, and its honest boundary

Blocking four tools is easy. Blocking a shell is not: bash can do anything. So the policy does a string scan over the command, segment by segment, and refuses the obvious mutators.

The design document publishes the false-positive / false-negative table rather than hiding it:

InputVerdictWhy
ls -la, cat x, git status, rg fooallowreads
cargo build, cargo test, make, tsc --noEmitallowread-only builds — artifacts are not a workspace mutation
rm -rf build, mv a b, sed -i, tee f, >fblockmutate
git commit -m x, git checkout -- ., git pushblockmutate history / remote
cargo fix/fmt/install, npm/pnpm/yarn install, go mod tidy, pip installblockmutate the source tree / lockfiles
echo hi > /tmp/xfalse positivewrites outside the workspace — blocked anyway, and that is acceptable
python -c 'open("f","w")'false negativean arbitrary mutator hidden in an interpreter
./build.shfalse negativeside effects unknown
Why not sandbox it?

Because a sandbox would have to be a container, a seccomp profile, or an LSM policy — a dependency and a platform matrix, for a mode whose actual job is "make the model stop and think". The guardrail is cheap, transparent, and refuses the mistakes that actually happen. Someone determined to write a file can always run perl -e; that is not the threat model.

10.3The prompt section

A refusal teaches the model what not to try; it does not tell it what to do instead. The section does — including the exit instruction, so the model hands control back rather than looping.

Note the two affordances the section leans on: todo is not blocked, and the user is told the exact command to switch modes. The plan therefore has somewhere to live, and the hand-off is explicit.

10.4How the toggle works

/plan (bare) toggles; /plan on|off sets. In the TUI it travels as Request::SetPlanMode { on }, which the actor applies to the agent.

Three details follow from that implementation, and all three are worth knowing:

  • It takes effect on the next run. An in-flight run cloned the system prompt into its LoopConfig at start; the toggle does not retroactively rewrite it.
  • Off restores the base prompt exactly. There is no accumulation of sections across toggles, because base_system is tracked separately.
  • It is never persisted. /new and /resume both start with plan mode off — a safety property, since a forgotten "on" would silently disable editing in the next session.

The TUI shows the state in the composer's foot line as ⏻ plan; the REPL prints a notice on each toggle. The TUI's /help lists toggle plan mode (explore, don't mutate).

10.5A separate, always-on gate

Do not confuse plan mode with BashRiskHooks. They are different policies with different lifetimes, and both can be active:

PlanModeHooksBashRiskHooks
WhenOnly while the flag is onAlways
ScopeFour editing tools + mutating shell commandsA catastrophic subset of shell commands only
Disabled by/plan offNothing — no config knob
PurposeKeep the agent in the planning phasePrevent destroying the machine
Shared withWorkers inherit the handleThe scheduler's Script nodes run under it too

That last row matters for workflow mode: a script node executes under the same before_tool_call gate as bash, so a policy refusal fails the node visibly instead of silently skipping it.

10.6Working in plan mode

  1. Turn it on and say what you want /plan then your request The model reads, searches, runs read-only commands, and proposes.
  2. Argue with the plan normal turns Cheap: nothing has been written, so a wrong plan costs a message, not a revert.
  3. Have it record the plan as a todo list todo with status pending The list persists in the session, so it survives a resume — and /verify renders its progress later.
  4. /plan off and say "execute it" the same conversation The model already has the plan in context; the editing tools come back online.
The one thing plan mode buys you

It moves the expensive mistake from "a wrong edit, discovered in review" to "a wrong sentence, discovered in reading". That is all it does — and it does it without a permission dialog, a staging area, or a second model.
