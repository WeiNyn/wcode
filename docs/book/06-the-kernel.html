Part III · Inside · Chapter 06

The kernel

wcode-harness is the part that must be correct: a turn loop, a tool protocol, a hook seam, and a streaming adapter. It knows nothing about terminals, config files, or teams — and that ignorance is what makes four clients possible.

6.1One loop, one turn at a time

run_loop is a function, not a task: it owns the run, drains three channels, and returns a RunResult. Everything else in the kernel is in service of it.

LoopConfig is the entire surface of a run:

FieldWhy it is a parameter
system, tools, llm, stream_fnWhat to say, what it may call, which model, over which transport.
hooksThe policy set — the only way to change behaviour without editing the loop.
steering, follow_ups, cancelThree input channels: inject at the next turn boundary, queue after the run, or stop now.
working_dirPlumbed explicitly so an embedded agent can run against a directory other than the process cwd.
max_turnsCaps a runaway tool loop. Default DEFAULT_MAX_TURNS = 100 (loop_.rs:15).
parallelWhether concurrency-safe calls in one batch fan out. --sequential turns it off.
compactionThe policy from Chapter 05, consulted before each request.
ctx_snapshotA read-only window the loop republishes at each turn boundary, so a client can ask mid-run questions without the &mut the run holds.
sessionOptional JSONL sink; each produced message is persisted as it is pushed.

Anatomy of a turn

  1. Check the turn budget loop_.rs:139 turns >= max_turns ends the run on a completed boundary — the final turn's tool results are already in context, so no call is left unpaired.
  2. Drain steering loop_.rs:149 Every queued Message is announced (MessageStart/MessageEnd), persisted, and pushed into context — so an interruption is visible in the transcript, not spliced in invisibly.
  3. Transform context, then compact if near the ceiling loop_.rs:166 Hooks first (they may rewrite history), then auto-compaction — best-effort: a summarizer failure must not abort a run that can still proceed.
  4. Stream the model Deltas become MessageUpdate; thinking becomes its own event; a stream error is fed back as a turn rather than killing the run (bounded by DEFAULT_MAX_STREAM_ERROR_TURNS).
  5. Execute the batch Tool calls are dispatched with policy first (before_tool_call), each emitting ToolExecutionStart → Update → End. Results are appended in call order, whatever the execution order.
  6. Loop or stop No tool calls → the turn is final. Tool calls → another turn. A cancel token firing at any point yields StopReason::Aborted.
Why MaxTurns is not an error

It is a safety valve, not a failure: the conversation is consistent, the session is intact, and the next turn can continue. Callers map it to a non-zero exit (-p prints "task may be incomplete"), but nothing is lost.

6.2Parallel tools, without races

Models routinely emit several tool calls in one message. Running them serially wastes the round trip; running them blindly races reads against writes. wcode lets a tool opt in to concurrency, and treats everything else as a barrier.

In practice: read, grep, find, ast_search and webfetch opt in. bash, edit/edits/write, and anything that mutates shared state (task, message, spawn) are barriers — so no read can race a write inside a batch. --sequential or [tools] parallel = false restores strict one-at-a-time execution.

6.4The actor: one mailbox, one writer

A SessionActor turns an Agent into a task with an inbox and a subscribable outbox. Callers send Requests and observe AgentEvents; nobody holds the Agent itself.

Two behaviours matter and are easy to miss:

  • One request at a time. A run holds an &mut on the agent, so anything arriving mid-run is parked and serviced afterwards — except the requests that have a defined mid-run answer.
  • Reads answer from the last turn boundary. GetHistory, Status, Usage, and SideAsk are answered from a snapshot instead of being refused, so the TUI can show a transcript and a member can be peeked while it works.
RequestMid-run behaviour
SubmitParked; starts the next run.
NotifyAppended to the conversation, no turn — the "tell, don't ask" mode.
InterruptInjected at the next turn boundary of the in-flight run.
WakeRuns a turn even if idle — how a scheduler dispatch and a worker report arrive.
CancelStops the run (and any retry wait). Idempotent.
SetModel/SetEffort/SetPlanModeApplied at the boundary; plan mode also recomposes the system prompt.
SideAskAnswered tool-free from the current context, never recorded.

6.5The streaming adapter

The kernel does not import a vendor SDK into the loop. A run receives a StreamFn: context, system prompt, tool definitions and options in; a stream of events out.

rig_stream_fn() is the built-in OpenAI-compatible adapter. It handles three things the loop should not know about:

  • Endpoint selection. chat or responses — and auto derives it from the model id (D025).
  • Effort mapping. Chat sends reasoning_effort, Responses sends reasoning: { effort }; unset sends neither.
  • Stalls and retries. A connect or first-item stall, and an inter-item idle gap, are bounded separately; transient failures retry with exponential backoff, capped.

Defaults: 3 retries, 500 ms base, 8 s cap, 60 s to first token, 120 s idle — all tunable in [retry] or by the matching WCODE_RETRY_* variables. Two zero conventions matter: ttft = 0 and idle = 0 disable that timeout, and retries are announced as Retrying events so a slow run explains itself.

Why an adapter and not an SDK call

The kernel's job is the loop. Provider quirks — SSE shape, effort naming, retry semantics — live behind one function pointer, which is also how a test substitutes a fake stream with no network at all.
