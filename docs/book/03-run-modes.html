The three run modes

wcode has exactly one entry point and picks a surface from your flags and your terminal. Knowing which branch you landed in explains almost every "why did it do that?" — from exit codes to whether Ctrl-C kills the process or just the turn.

3.1The decision tree

dispatch is the fork in the road. It reads the parsed flags in a fixed order and never revisits the choice.

You typedYou gotEnds when
wcode -p "…"One-shot: one turn, reply on stdout, exit.the turn ends
wcode --agents --task "…"Headless workflow: a plan is driven to terminal state.the plan settles (terminal_code)
wcode serve …The process owns the session and serves it over a socket/stdio.the client disconnects
wcode --socket … -p "…"A client of a session served elsewhere.the turn ends
wcode (TTY both ends)TUI — the full-screen client.you quit
wcode (piped / CI)REPL — the line client.EOF or /exit

Two things follow from that table and surprise people: -p never starts a TUI even on a terminal, and piping input forces the REPL even if you wanted the TUI. Both are deliberate — a pipe cannot render an alt-screen, and a script cannot answer a prompt.

3.2One-shot (-p)

The simplest contract in the program: text in, final assistant text out, a meaningful exit code. The reply is the last assistant message — not a concatenation of the streamed deltas.

stdout

Only the final assistant text. Nothing else — so wcode -p … | jq style plumbing works.

stderr

Errors, the provider diagnostic at startup, retry notices, thinking and tool lines.

exit

0 clean · 1 model error, max turns, or session closed.

Why a drain task runs alongside

one_shot subscribes to the event stream and awaits the reply. The drain captures what the reply does not carry — the last stream error and the last MessageEnd text — so a failed run can still report the real cause instead of a generic exit.

3.3The REPL

A readline-flavoured loop with /-commands, prompt history, and one important asymmetry: Ctrl-C aborts the run, not the program. Press it while idle and it exits.

Unknown /… lines are not errors — they are sent to the model as prompt text, so a leading slash in prose does not derail the turn.

The full command table (including /btw, /usage, /sessions, /skill) is in Chapter 05 and Chapter 15.

3.4The TUI

The default interactive surface on a terminal: a full-screen ratatui client over the same AgentEvent stream. It is not a different agent — it is a different renderer, running in the same process over the same session.

Chapter 04 covers it properly. The one thing to know now: with a team, each member is its own surface, and typing goes to the focused one.

3.5Typing while it runs

In the TUI and REPL you can submit while a turn is in flight. The input is queued, not dropped and not interleaved: it starts at AgentEnd, as a fresh turn, on the surface that owns the queue.

Only the foot line shows a count (⇥ N queued); the queued text is not rendered as a transcript block until it actually runs. So the transcript never shows a user message that has not happened yet.

3.6Choosing, in practice

I want to…UseWhy not the others
ask one question in a script / CI-pexit code + pure stdout is the whole point
work for an hour with a model, editing filesTUIthe REPL reprints a lot; the TUI keeps a scrollable transcript and a live status band
run over SSH in a dumb terminal--no-tuithe alt-screen and mouse capture need a real TTY
drive a feature to a pull request, unattended--taskworkflow mode is the only mode with a terminal exit code for a plan
keep one long-lived session, attach several clientsserve + --socketa client cannot fork the kernel; the server owns it
What --no-session really means

It skips the JSONL transcript — no resumable file, no resume: line at exit, and a headless workflow run gets no run.json either (so no resume: promise it cannot keep). The conversation still exists in memory for the life of the process.
