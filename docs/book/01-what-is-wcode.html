What wcode is

A terminal coding agent with a small kernel and no opinions you cannot delete in code. This chapter is the thesis: what wcode optimises for, what shape that gives the repository, and which features it deliberately does not have.

1.1The one-sentence version

wcode streams an LLM conversation to your terminal, gives the model a handful of content-addressed tools — numbered reads, literal-text edits, grep/find, a shell — and stays out of the way. It speaks to any OpenAI-compatible chat-completions endpoint, so the model is a setting, not a dependency.

The design goal is not "the most capable agent". It is the smallest agent that is still pleasant to supervise: one event loop, one tool protocol, one session format, and a policy seam (Hooks) where everything situational lives as code rather than as configuration.

1.2Shape: a kernel and its clients

Five pieces, and only one of them knows how to think. The kernel owns the loop; every other crate is either transport or presentation.

CrateRoleLines (src/, pre-test)

Fourteen modules. Nothing in that list knows what a terminal is, what a config file is, or what a "team" is — which is exactly why a TUI, a VS Code webview, and a socket server can all be built on it without forking the loop.

1.3The seam: events down, hooks in

The kernel exposes exactly two interfaces to the outside world, and both are narrow.

Out · AgentEvent

Everything the run does becomes a value: TurnStart, MessageUpdate, ToolExecutionStart/Update/End, TurnEnd, Compaction, Retrying, MessageReceived, Error. A UI is a function from that stream to pixels — it cannot reach into the loop, and the loop cannot reach back.

In · Hooks

Seven call sites: transform_tool_input, before_tool_call, after_tool_call, before_inbound, transform_context, should_stop_after_turn, after_run. Every policy wcode has — plan mode, bash risk, the verify gate, report-back — is one implementation of this trait.

before_tool_call returning Some(reason) is the important one: the tool does not run, and the reason is fed back to the model as a blocked: … tool error. That single return value is how plan mode refuses writes, how a catastrophic shell command is stopped, and how an unverified work node is refused — three policies, one seam, zero configuration.

1.4What wcode deliberately does not have

The repository's own guidelines state it plainly: Minimalism is the point. Absent by design:

Not presentWhat people expect insteadWhat wcode does
MCP A plugin protocol, servers, tool discovery at runtime Tools are Rust TypedTools compiled in. Adding one is a small diff, not a config entry.
Permission prompts "Allow this command?" dialogs, allowlists on disk BashRiskHooks refuses a fixed set of catastrophic commands; everything else is allowed. The human supervises by reading the transcript, not by clicking.
Approval flows A review queue, a staging area, a "apply" button Diff is shown inline; the edit already happened. Git is the undo.
Config files for behaviour agents.toml, rules/, policies.yaml Implement Hooks. Build the variant you want instead of configuring one.
Why this is a feature, not an omission

Every knob is a code path that must be documented, defaulted, validated, and kept working. wcode's answer is: if a policy matters to you, it is a type in your program. The cost is that you cannot tune it from a TOML file. The benefit is that there is nothing to tune — and therefore nothing to drift.

1.5Content-addressed, not line-addressed

One decision shapes every tool, so it belongs in the introduction rather than buried in Chapter 08. Agents corrupt files when they address positions: insert a line and every line number below means something else. So wcode has no line-address primitive at all. edit replaces an exact literal old_string; a miss writes nothing.

The match is the staleness check — if the file changed since the read, the text no longer matches. There is no anchor store, no digest guard, no session memory of what the file used to look like. Chapter 08 is the full argument.

1.6Scale, honestly

Kernel

8.2k lines pre-test. Small enough to read in an afternoon; it is the part that must be correct.

One binary

cargo install --path crates/wcode-cli. No runtime, no Python, no node — unless you want the VS Code client, which needs node.

Zero daemons

A session is a process and a JSONL file. serve is opt-in, not the default posture.

1.7Where to start reading the code

  1. crates/wcode-harness/src/loop_.rs ~ the heart One turn = one model call + the tools it produced. Read this before anything else; every other module is a service this loop uses.
  2. crates/wcode-harness/src/agent.rs state above the loop Conversation history, model/effort switching, compaction, cancel, side questions.
  3. crates/wcode-cli/src/main.rs the composition root Flags → config → hooks → tools → agent → surface. If you wonder "who sets this?", it is probably here.
  4. crates/wcode-cli/src/tools/ the concrete tools One file per tool. Small, typed, individually tested — the best template for your own.
  5. crates/wcode-cli/src/tasks.rs + scheduler.rs the team machinery Read after Chapter 12, not before.
