Part IV · Teams & pipelines · Chapter 12

The task DAG

The plan is a graph the root owns: nodes, blocked-by edges, artifacts as the hand-off, and gates whose rejection sends work back. It is journaled, so a crash costs a restart rather than the plan — and a scheduler, not the model, decides what runs next.

12.1Why a graph at all

A flat todo list cannot express "verify waits for implement, and a failed verify re-opens implement". A tree cannot express "ci waits for both implement and publish". A DAG can express both, and its acyclicity gives one useful guarantee: readiness is computable.

The plan is root-owned. Only the root gets the task tool, so only the root plans; a worker keeps its report-back. That asymmetry is what lets the scheduler trust the plan.

12.2The node

Five states · tasks.rs:45

Todo → Doing → Done. Two terminals: Failed (the rework cap was hit; dependents stay blocked forever) and Skipped (an incoming edge's condition was false — terminal, but satisfied for readiness, so a pruned step never stalls the DAG).

Two run kinds · RunSpec

Session { member, timeout_secs } — a worker produces the outcome. Script { command } — sh -c under the bash policy; the exit code is the verdict.

Readiness is derived, never stored

No ready flag, no blocked counter to keep in sync. Every mutation publishes a snapshot on a watch channel and readiness is recomputed from it — which is why the TUI, the scheduler, and task list can never disagree.

12.3Edges, and two kinds of dependency

DepMeaningReadiness
Id(n)Plain blocked-by.n must be Done or Skipped.
Edged { id, condition }Blocked-by and guarded: a script test (exit 0 = taken) or a judge verdict.All deps satisfied, then every incoming condition AND-folds to "take".

A false condition makes the target Skipped — it never runs, but its own dependents become ready anyway. That is the difference between pruning a branch and deadlocking on it. A policy refusal (rather than a false test) blocks and escalates instead; it is never laundered into a silent skip.

That guard is why an out-of-order complete is an error rather than a state-machine corruption: the model cannot mark work done before its inputs exist.

12.5Gates and rework

gate = true inverts what a verdict means. A normal node's complete says "this is finished"; a gate's reject says "the work it depends on is not".

Three things to notice: the whole downstream cone is invalidated (not just the immediate predecessor), the reason becomes the node's feedback — so the next run is hydrated with it — and the cap is max_attempts (default 3, settable as [workflow] max_attempts).

A gate is shape, not verification (D002)

Completing a gate means the root model accepted the work. Nothing about the gate proves the diff is correct. That is not a gap to be fixed with more machinery — it is where the human (or a reviewer role with an actual rubric) belongs.

12.6R′: the verify gate as structure

"Ask a reviewer" is a reminder a model can skip. VerifyGateHooks turns it into a structural precondition: a work node cannot be completed unless some gate depends on it directly.

If the call is…Verdict
not a task callallow (the hot path)
task with op ≠ completeallow — create/assign/depends/reject/reset/list
complete of a real gate (gate ∧ ≥1 dep)allow — that is the approval
complete of a Script nodeallow — the exit code was the verdict
complete of a node some gate already depends onallow
complete of an un-gated Session work nodeblocked, with the reason above

A blocked call does not run, and the loop feeds blocked: … back to the model — which then creates the gate and assigns it. That is the whole enforcement: no new tool, no new state, one predicate over the snapshot.

Consequence for template authors

Every Session work node needs a consuming gate, or the plan deadlocks at complete. The shipped pipeline has an explicit explore → review-sketch edge for exactly this reason: without it, task complete explore is refused. A dep-less gate: true node is not an exemption — it is a degenerate bypass whose own reject would error.

12.7Journaled, so a crash is a restart

Every public mutation records one journal line (PlanOp) to <groupdir>/plan.ndjson: Create, Depends, Assign, Configure, Start, Complete, Reopen, Reject, Reset, Fail, and a Restart written on load.

Two invariants that make resume safe

Doing → Todo on load

A node that was in flight when the process died is restarted, never assumed complete. This is why the scheduler must be spawned after the plan loads — otherwise a Doing node would never re-enter ready_ids().

reset_epoch

reset bumps a counter even when every other field is already at its reset value — the one signal that makes a reset observable to the scheduler's block-and-escalate bookkeeping.

The scheduler's in-memory deadline map is deliberately not journaled: a crash is not the node's fault, so a resumed node gets a fresh deadline rather than timing out for work it never got to do.
