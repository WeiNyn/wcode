Editing by literal text

The single most consequential decision in wcode: there is no line-address primitive. An edit names the text it replaces. Everything else — the error codes, the batch semantics, the absence of a staleness guard — falls out of that one choice (D007).

8.1The failure this prevents

Line numbers are positions. The moment one line is inserted above, every number below refers to a different line — silently. A model that read a file, then applied two edits in one pass, is the classic corruption story: the second edit lands on the wrong region, or on a region that no longer exists.

wcode removes the failure mode by removing the primitive. read still prints numbers, because a human and a citation both need them — but they are locators, never addresses.

Note what is not in that struct: no start line, no end line, no line count, no offset, no hash. The address is the text.

8.2Byte-exact means byte-exact

Matching is a literal substring search over the file's bytes. Tabs are not spaces; a trailing space is significant; a missing blank line is a miss. That strictness is the safety property — a fuzzy match is a guess, and a guess is how an agent edits the wrong thing.

CodeConditionWhat the model is told
E_NO_MATCH old_string occurs zero times "The match is byte-exact — re-read the file and copy the text (whitespace counts)."
E_AMBIGUOUS_MATCH It occurs more than once and replace_all is not set The occurrence count, and two fixes: include more surrounding lines, or set replace_all.
E_EMPTY_OLD_STRING old_string is empty "There is nothing to match — give the exact text, or use write for a whole-file rewrite."
Errors are a contract, not noise

Every message names the code and the fix. A model that reads "include more surrounding lines" can recover on the next turn without a human; a model that reads "edit failed" cannot. The wording is part of the tool's interface.

8.3The match is the staleness check

Older designs (including an earlier wcode) addressed a range by two hash anchors, and needed a separate whole-file digest guard to cover the span between them. Text matching covers that span by construction: if the file changed anywhere inside the region you named, your text no longer matches.

So there is no anchor store, no digest cache, and no session memory of file state. Three consequences, all good:

  • An external edit — bash, a formatter, another process — is picked up automatically, because nothing is cached.
  • Nothing to invalidate, so nothing to get stale.
  • The tool is stateless, so it works identically in a fresh process, a resumed session, or a worker that has never read the file.
A note on [workspace] digest_cas

The README still documents a [workspace] digest_cas key for whole-file compare-and-swap. At this commit no such code exists — the digest machinery was removed with the anchor scheme (7c740fe). The book follows the code: there is no digest guard, by design. Treat that README section as stale.

8.4One edit, and a batch of edits

A single edit is one op. A model often needs three coupled changes in one file; issuing three separate calls means a partial success is possible, and a partial refactor is worse than a failed one. edits makes the batch atomic.

In order, against accumulating content

Op 2 matches against what op 1 produced. That makes rename-then-reference safe: the second op can depend on the first having happened.

All-or-nothing

A failing op refuses the whole call. The repository has a test that asserts op1 must not land when op2 fails (edits.rs:212).

There is no dry_run flag. The diff is returned on success and shown in the transcript, so "review before applying" is a reading step, not a mode — and git is the undo.

8.5When writing the whole file is right

write is the escape hatch, not the default: it creates parents, overwrites, and writes the content byte for byte — no reformatting, no trailing-newline tampering, indentation preserved exactly.

It is the right tool when:

  • the file is new;
  • the change is most of the file (an old_string that long is a liability);
  • you are deliberately regenerating a file whose content is derived anyway.

It is the wrong tool for a one-line change in a 600-line file: you would be re-typing 600 lines the model must reproduce exactly, which is precisely the failure mode literal editing exists to remove.

8.6The practice that follows

  1. Read the region you intend to change read with offset/limit, or grep for the anchor line You are collecting text to paste, not a line number to point at.
  2. Make old_string unique and small 2–6 lines usually suffice Include the function signature or a neighbouring line when the body alone is ambiguous. On E_AMBIGUOUS_MATCH, add a line — do not reach for replace_all unless you truly mean every occurrence.
  3. Group coupled changes into one edits call all-or-nothing A rename plus its three call sites is one atomic intent.
  4. Read the diff in the transcript ToolExecutionEnd carries it The diff is presentation-only — it never enters the model's context, so it costs no tokens and never becomes something the model "remembers" instead of the file.
Why this survives parallelism

Because matching is content-addressed, two agents editing disjoint regions of the same file cannot silently clobber each other — a lost update means the text no longer matches, which is a refusal rather than corruption. The mutation lock (Chapter 07) makes the writes atomic on top of that.
