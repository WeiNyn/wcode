Protocol & clients

The same Request → AgentEvent conversation that runs in-process can run across a socket or a pipe. That is what makes a TUI, a VS Code webview, and a remote worker all clients of one kernel rather than forks of it.

14.1The seam that makes it cheap

Client code targets Backend, never Agent. Two variants — Local (an in-process SessionHandle) and Remote (a socket Client) — and the rest of the program cannot tell them apart.

This is why there is no separate "remote mode" in the TUI: --socket swaps a constructor argument. Two features are honestly client-side and therefore refused over a socket — /new and /reload, both of which re-exec the process.

14.2One frame, one line

The wire format is newline-delimited JSON: one object per line, the body flattened into the envelope so a frame is a flat object on the wire.

Three properties fall out of that envelope, and each solves a problem a naive protocol would have:

reply_to separates answers from streams

A client's ask resolves on the matching reply_to while streamed events keep arriving on the same connection. No multiplexing dance, no second socket.

session is the address

A server demuxes a request to the handle named by its frame, and stamps every event with its origin. One connection can carry a whole team.

v is a major version

PROTOCOL_VERSION = 1. Unknown request variants deserialize to Unknown and are answered Ack — an old server reading a new request reports "unavailable", never a wrong answer.

14.3The request vocabulary

The same enum is used in-process and on the wire. Two families: requests that name an Agent method, and requests the transport answers.

The last three "name no Agent method" — so an in-process session answers them with Ack (read as "unavailable"), while a server intercepts them. That is how the same enum serves both worlds without a capability bit.

14.4Serving

CommandTransportNotes
wcode serveUnix socket at ~/.config/wcode/wcode.sockThe default path sits beside the config, so both ends agree without an argument.
wcode serve --socket /pathUnix socketExplicit path.
wcode serve --stdiostdin/stdoutAny platform; one client; implies serve.
wcode --socket /path -p "…"clientOne turn against the served session.

Each connection gets a writer draining an outbound queue, one fan-out task per served session, and a read loop that demuxes inbound requests to the handle named by the frame. The roster is live: a session registered after the server started — a worker the orchestrator spawns mid-run — is fanned to every connection, and the grown roster is pushed as an unsolicited Sessions frame, so a client learns new ids without polling.

What does not work over stdio

--task is refused with serve at the boot guards, and a headless workflow needs a process exit code that a served session cannot express. In-process --agents with a team works fine over --stdio; the workers are in-process, so no socket is involved.

14.5A served session as a worker

The same protocol runs the other direction: serve can publish this session as somebody's worker.

A root can also define a worker on a peer with spawn { to: "w7" }, which travels as Request::Define and is answered Spawned. On the peer, the worker is registered in its own registry — so the remote session can message its owner back through the same permission model described in Chapter 11.

Fire-and-forget deliveries to remote peers are flushed before exit (flush_all with a bounded timeout), so a message sent in a one-shot run is not lost when the process drops the runtime.

14.6The VS Code client

editors/vscode/ is a second client, not a second kernel. It spawns wcode serve --stdio and speaks the same frames as the TUI — which is why a behavioural feature never has to be implemented twice.

PieceWhat it is
Extension hostTypeScript: spawns the binary, owns the connection, routes frames.
WebviewThe UI. Deliberately dependency-free; syntax highlighting runs host-side on Prism (D008).
TabsEach editor tab is an independent wcode session (D013).

Reading measureAdaptive, not a fixed column count (D014).
Why "presentation only" is a hard rule

A client that can change behaviour becomes a second source of truth — and then two clients disagree. So the extension can restyle text, and cannot decide whether a tool runs. Every behavioural knob lives in the kernel or in a Hooks impl, where both clients inherit it.

14.7What this buys, concretely

Attach late

Start a long session with serve, disconnect, come back with a client — the kernel never stopped, and the roster arrives on connect.

Watch a team from one place

One socket carries the root and every worker, each event stamped with its origin session. That is what the TUI's surfaces and sidebar consume.

Split a team across machines

--peer plus serve --owner makes a worker remote without a new concept: it is still an address, a permission edge, and a mailbox.

Test without a terminal

A client is a frame producer. The protocol is testable with strings and a pipe, which is how the transport is tested today.
