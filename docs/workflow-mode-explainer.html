Workflow mode: a pre-seeded DAG,
not a conversation the root improvises

wcode has one orchestration substrate — a shared task list, a registry of worker sessions, a scheduler. What changes between agent-team mode and workflow mode is where the plan comes from and who is allowed to drive it. This report traces both paths through the real code and pins every claim to a file:line.

01Two modes, one machine

Both modes run the same code: an Orchestrator (root session + Registry + TaskList), a detached Scheduler, a ReportBack hook that turns a worker's last message into a Wake to the root, and a VerifyGateHooks policy that refuses to close a work node nobody verifies. The scheduler is spawned for any orchestrator — team mode included.

So the difference is not "with scheduler" vs. "without". It is three narrower questions:

Where the plan comes from

Team: the root model calls task{op:"create"} turn by turn.
Workflow: instantiate_workflow creates every node at boot from TOML.

Who may grow it

Team: the root — create/depends/assign are its normal tools.
Workflow: nobody, in the default posture; the seed prompt says "Do NOT create nodes".

How the run ends

Team: the human quits the TUI/REPL.
Workflow: terminal_code() — the process exits 0/1/2 on its own.

The one-line answer

Team mode is an interactive loop where the root authors and completes a plan as work arrives. Workflow mode is a headless run where the plan is declared in TOML up front, the scheduler owns dispatch, and the root is demoted to a verdict relay: task complete / task reject.

02Mode A — the agent team (interactive)

Entry: wcode (a non-empty [team] auto-enables agents mode, main.rs:799) or wcode --agents. There is no --task, no plan template, typically no graph at all.

What boot does main.rs:1615-1639

Each [team] member is spawned as its own session and registered in the phonebook:

The root's system prompt then gains a roster block — the only "workflow" it knows is prose. Compare with mode B, where the same slot carries a graph-shaped brief.

What the root does, turn by turn

  • Plans. task{op:"create", title, deps?, gate?} — the tool doc is explicit that create hard-sets run: Session{member:None}, so a plan the model authors is always judgement nodes (crates/wcode-cli/src/tools/task.rs:152).
  • Staffs. task{op:"assign", assignee:"explorer"} resolves the name through the Phonebook and writes task.owner — the scheduler's dispatch key.
  • Delegates. Sparked or messaged. It may spawn a brand-new worker at any moment, or message an existing one — including a lateral question that has nothing to do with the plan.
  • Accepts. A worker's report arrives as a Wake; the root decides complete vs. reject in open prose.
  • Improvises the next step — the graph, if there is one, only exists because the model wrote it that way.
Shape, not ceremony

Team mode is not a free-for-all: VerifyGateHooks is installed whenever an orchestrator exists (main.rs:1513), so rule R′ still refuses closing a work node no gate consumes — in interactive sessions too. The difference is that the root must invent that gate itself.

Where it is observed

The TUI: each member is a surface you can switch to (Ctrl-N), the plan shows under /tasks, the sidebar lists the roster. The run never "finishes"; you close it.

03Mode B — the workflow (headless)

Entry: wcode --agents --config X.toml --task "…". The [workflow] table is a plan template, and per D001 it is inert without a task:

Two of those three conjuncts are load-bearing: has_task means a template with no run exits with the notice "workflow: present but inert (no --task)" (main.rs:1381); !resuming_group means a resume loads the journaled plan instead of re-seeding it — otherwise the plan would double on every resume.

The run is a wrapper around a driver

The root gets exactly one opening instruction, and it is a fence: the plan exists; do not build another one.

Note "Do not message its member directly" — in workflow mode the only sanctioned route into a worker is the scheduler's dispatch. Lateral messaging still exists, but only along declared edges (see §11, D030).

Then it just waits for the plan to settle

The exit verdict is a pure function of the plan, not of the model's summary: Some(1) the moment any node is Failed (fail-fast — its dependents can never progress), Some(0) once every node is Done or Skipped, None while running.

04Boot: config → validated graph → plan

Three gates stand between a TOML file and a live plan.

  1. Structural validation (config.rs:1057 validate_workflow_structure): unique node ids, one edge per (from,to) pair, no self-edge, both endpoints known, a gate needs ≥1 incoming edge, an edge condition is exactly one of script/judge, scripts non-empty.
  2. Acyclicity (config.rs:1175 topo_order): the graph is walked to produce creation order, which is why an edge may legally name a node authored later in the file.
  3. Member resolution (config.rs:1155 validate_workflow_members, called at main.rs:793): every member must exist in the folded team — including markdown agent definitions — so a typo cannot silently produce an undispatchable node.

create writes a Todo node and journals a Create line; assign writes owner (agent:<member>); configure writes the RunSpec + gate. All three are replays: the same file plan.ndjson rebuilds the identical graph on resume. {{task}} is substituted into titles only — never into scripts (config.rs:469 node_title).

05The scheduler loop — one place that decides "what now"

Scheduler::run is a single tokio::select! loop over four wake sources: a plan change, a judge verdict, a node deadline, and nothing at all.

Dispatch: a Wake for a session, a subprocess for a script

The hydration is what makes a workflow node self-contained. A worker is not told "look at the plan"; it receives its own title, every dependency's artifact, and the last reject reason if this is a rework:

A Script node never sees a model. Its command runs through the same before_tool_call policy the bash tool uses, and its exit code is the verdict: 0 → Done, non-zero → reject (or fail at the cap), killed → fail (scheduler.rs:591-655).

06The data model both modes share

Five states · tasks.rs:45

Todo → Doing → Done, plus two terminals: Failed (rework cap hit; dependents stay blocked forever) and Skipped (an incoming edge's condition was false — terminal, but satisfied for readiness, so a pruned step never stalls the DAG).

Readiness is derived, never stored · tasks.rs:1068

ready_ids() = Todo ∧ every dep Done or Skipped. The scheduler keeps only "ready ∧ (has an owner ∨ is a Script)", so an unowned session node is silently never dispatched rather than looping.

In team mode this exact struct is filled in by the task tool; in workflow mode by instantiate_workflow. Everything downstream — frontier, hydration, escalation, the TUI's /tasks rendering, the journal — is shared, and therefore identical.

07Gates, rework, escalation

gate = true inverts what a node's verdict means: a gate judges its dependencies, so rejecting it sends the work back rather than closing the gate.

Past the cap the node is Failed and the scheduler wakes the root with a Wake from its own address scheduler (which the orchestrator gives an ownership edge to the root, or deliver would be NotPermitted — agents.rs:834):

task reset <id> is the escape hatch: it bumps reset_epoch, which also re-arms a node the scheduler had blocked as unjudgeable.

R′ — the verify gate is structure, not a reminder

The hook's decision table (verify_gate.rs:117) is small and total: non-task calls pass; only op:"complete" is examined; a real gate (gate ∧ ≥1 dep) passes; a Script node passes (its exit code is the verdict); a node a gate already depends on passes. Everything else is refused, and the loop feeds blocked: … back to the model. D002 is the honest caveat printed in every design doc: a gate proves the step ran, never that it was right.

Consequence for template authors

In .wcode/workflow.toml there is an explicit explore → review-sketch edge that looks redundant. It is not: R′ demands a gate with a direct dependency on every work node, so without it task complete explore is refused and the pipeline deadlocks at node #1.

08Bounds, exit codes, resume, status

One rule, stated once in the scheduler and honoured everywhere: no limit unless set. Both None (key absent) and Some(0) mean unbounded — never a zero-length kill. v0.12.0's hard-coded 300 s script cutoff is gone (D033, amended).

The observable surface of a headless run:

  • stderr — a per-event log (root reports + every node-state change: #id [state] title); --quiet silences it.
  • stdout — the final per-node summary, always (print_workflow_summary, main.rs:2780).
  • --status [group|latest] — the read-only counterpart, which reads plan.ndjson through TaskList::read_at and deliberately not load_at (that would journal a Restart into the file being inspected — main.rs:2793).
  • resume: — any non-zero exit from a created run prints a copy-pasteable relaunch line carrying the same cap; the task text lives in <groupdir>/run.json.

The invariant that makes this cheap

Both modes mutate the same TaskList through the same journal and are rendered by the same TUI reducer. Workflow mode adds a seeder (config → plan) and a driver (wait for terminal), not a second engine.

10Worked trace: the shipped feature pipeline

The declared template .wcode/workflow.toml

Life of one node

  1. Scheduler dispatches implement scheduler.rs:567 → Registry::deliver(Request::Wake) Content = #5 implement + #3 showed: artifact + any Revise per this feedback: block. Node flips Todo → Doing, its dispatch instant enters the deadline map.
  2. The developer session runs its turn crates/wcode-cli/src/agents.rs:492 → ReportBack When it ends, after_run delivers its final message to the root as a Wake. A failed/aborted worker synthesizes a status line instead, so the root is never left waiting.
  3. The root relays the verdict crates/wcode-cli/src/tools/task.rs:152 task{op:"complete", id:5, artifact:"…"}. Before the write, VerifyGateHooks checks R′: does a gate depend directly on #5? Yes (verify), so the call passes.
  4. complete stores the artifact and publishes tasks.rs:856 Refuses if a dep is unsatisfied. The watch publish wakes the scheduler, whose next frontier is now verify.
  5. verify is a gate, so a reject means "send it back" tasks.rs:1021 reject → reopen_inner Every dep of the gate and its whole downstream cone return to Todo with the reason as feedback; the gate itself returns to Todo rather than "finishing". Attempts are bumped; past max_attempts the node becomes Failed.
  6. Everything settles → the process exits main.rs:2713 → tasks.rs:1097 terminal_code() returns Some(0) → summary on stdout, exit 0. Some(1) → summary, a resume: line, exit 1.

11Gotchas that are decisions, not bugs

D001 — fenced to --task

A template without a task is inert by design: `workflow: present but inert (no --task)`. Headless without a task would have no human to approve a plan, and interactive use would fight the root's own planning.

D002 — a gate is shape

The gate proves a step ran. The verdict is still the root model's. This is stated in the code comments, the README and the shipped [orchestrator] guidelines — deliberately, so nobody mistakes a green gate for a correct diff.

D029 — a skip prunes, never stalls

Skipped is terminal and satisfied. A false script condition or a judge SKIP takes that branch out of the run while its dependents still become ready. A policy refusal, by contrast, blocks and escalates — it is never laundered into a skip.

D030 — lateral messaging is edge-scoped

At boot register_adjacency (main.rs:2924) calls allow_pair for each edge whose both endpoints are member nodes, so edge-joined nodes may message each other — and nobody else.

D033 — no implicit bounds

An unset node/edge bound is unbounded. If you relied on v0.12.0's 300 s script cutoff as a backstop, set timeout_secs before upgrading: a wedged command now waits until the run cap.

Never sleep to wait

The root is told to end its turn rather than poll — a report is a Wake that only lands between turns. SleepRefusalHooks enforces it for sleep-leading commands, so a sleep-leading edge or node script cannot exist at all.
