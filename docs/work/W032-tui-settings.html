An editable settings panel in the TUI

A row cursor, arrow keys, Enter, Tab — and seven settings you can change without remembering a chord. Not a config editor: a face on the session setters that already exist. The interesting work is not the rows, it is that a modal here would destroy itself the moment it opened a picker.

1The ask

verbatim

the setting here is setting edit as model, control by keyboard (arrows, enter, tab etc)

Read precisely, that sentence contains three requirements and one analogy. Edit — not merely see. As model — the panel is an editor in the sense the /model picker is one: you land on a row, you change it, it takes effect. Keyboard — arrows to move and change, Enter to act, Tab to move between groups. And the analogy is the load-bearing part: whatever the panel does, it must feel like the thing it is modelled on.

The problem it solves is dispersion. Seven knobs live on chords with no command — Alt-[ (app.rs:4032), Alt-<digit> (:4034), Ctrl-G (:4036), Ctrl-B (:4037), Ctrl-O (:4043), Ctrl-T (:4046) — and the settings that do have commands (/effort, /plan, /theme, /width, /view) are one-shot verbs you have to already know. Nothing lists what is in effect, and nothing lets you change two of them without typing two commands.

the sentence that makes this cheap

Every row this panel edits is session state that already has a live setter. Nothing is written to config.toml, because nothing needs to be. Everything expensive about "a central setting" — persistence, merging, validation of a human's hand-edited file — is a different feature, and it is refused here on its own merits rather than smuggled in as a side effect.

2What v1 got wrong

withdrawn · the error named, not buried

v1 read the same sentence as "a place to see settings", recommended a read-only view, and argued against an editor because an editor implies a config writer. That inference was simply false — and it was used to refuse the feature that was actually asked for.

The inference fails on a fact about this codebase: the editable set and the config-file set barely overlap. Seven rows are session settings with existing setters. Of the four that also appear in config.toml, every one already has a runtime override path — /model, /theme, /width, /view. The repository had already decided how that split works, three decisions ago:

So the refusal that survives is narrow and worth stating exactly: no runtime config.toml writer. Not "no editing" — editing is the feature. The panel is the session half of D016's split, given a face.

One thing survives from v1 intact, and it is now load-bearing rather than a nice-to-have: the kernel getter. An editor that shows a value it cannot re-read is worse than a read-only view — you would be pressing keys against a number that might be a lie. §8 is that argument.

3The constraint that decides everything

A settings panel is a modal with a row cursor and, on the model row, an escape hatch into an existing picker. The obvious implementation — a new Overlay variant — cannot do that. Here is why, in three lines of code:

So a panel that is the overlay is destroyed the instant one of its rows opens a picker. Three ways out, and only one of them is cheap:

hostverdictwhy
Overlay::Settings(…) rejected Either a picker replaces the editor, or the variant carries its own sub-picker — which forces accept_picker off self.overlay.take() and a modal drawn inside a modal. More code than (c) for no gain.
Mode::Settings rejected Mode is the composer-ownership axis (app.rs:2372: "Input is the composer … Browse moves a selection over the committed transcript"). A panel is a modal, not a third owner — and a Mode sits below the completion popup in precedence.
App.settings: Option<SettingsState> chosen The panel's lifetime is independent of any modal's, so Enter on the model row opens the ordinary picker and the accept arm that already exists applies it (app.rs:5217–:5221): writes Status.model, echoes a transient, pushes Request::SetModel. Closing the picker reveals the still-open panel. Zero new accept code.

4The grammar

One cursor, no dirty state, no cancel. That is not a simplification — it is the only grammar that keeps the panel's one existing invariant, which a test pins: app.rs:9532 esc_closes_the_info_modal_and_nothing_else_does, over app.rs:5164 Key::Esc => self.overlay = None, // the only close key (Q2).

keyaction
↑ / ↓, PgUp / PgDn, wheel move the cursor (clamped); the wheel moves three rows, as the transcript does
← / → change the value on Nudge and Cycle rows; a no-op elsewhere
Enter act per row kind: flip a toggle, advance a cycle, open a picker, set a hint on a read-only row
Tab / BackTab jump to the first row of the next / previous section (session ⇄ config)
Esc close — the only close key, unchanged
anything elseswallowed

A two-level cursor (row, then cell) would force Esc to sometimes mean "cancel the edit" — breaking a pinned invariant to buy a commit model for setters that already apply immediately. So every act is immediate and Esc closes.

one invariant deliberately broken, one kept

Kept: Esc is the only close key. Broken: "Enter is swallowed". The Info modal swallows Enter for a mechanical reason — accept_picker's take() would destroy it (app.rs:9539–:9545). In this host take() removes the picker, not the panel, so Enter is safe. The Info test stays green untouched; a parallel test pins the new behaviour.

Tab is new grammar with no precedent — it is handled only in the completion popup (app.rs:4417), and BackTab only in the composer, where it means focus_prev (app.rs:4031). Inside the panel both are free, but because the panel swallows keys, BackTab no longer switches surfaces while it is open. That is a real consequence, named in KEYS so it is documented rather than surprising.

5The rows are data, not a switch pile

Five kinds, one key behaviour each. The only match in the module is over the kind — never over row ids — so adding a row is adding data:

rowkinddelegates to — a setter that already exists

Four of the seven act purely client-side (theme, width, view, sidebar) and settle instantly. Three push a Request (model, effort, plan) and can be deferred by the harness — which is what §8 is about.

6The panel, drawn

The cursor is ❯ in accent() — the picker's glyph (ui.rs:431), chosen over browse's gutter bar ▌ (ui.rs:719) and the mouse-drag REVERSED style (ui.rs:707) so the panel inherits one of the three existing conventions rather than inventing a fourth. Row bodies reuse item_line (ui.rs:253–:261), so the panel reads like F1 and /help: accent label, padded, dim detail.

Affordances sit at the right in dim — ‹ › for a nudge or cycle, › for a picker, [ ]/[x] for a toggle. The · pending mark is dim too, never a hue: error red is the only colour in the base palette (docs/tui-design.md §1), and a pending state is not an error.

one fewer thing to test

The scroll offset is derived from the cursor in the renderer (keep-the-row-visible), so SettingsState carries a single usize — no second scroll field and no second clamp rule, unlike the Info modal whose clamp arithmetic has two tests of its own (app.rs:9553, :9911).

7The one new vocabulary: effort

Everything else on the panel already has a value space somewhere. Effort does not — and that is a small, real design decision rather than a lookup.

No list in the TUI

/effort takes free text with three clear-synonyms ("-" | "none" | "off" → None, app.rs:4255). PickerKind has no Effort arm, and there is no effort picker.

No validation in the kernel

protocol.rs:262 SetEffort { effort: Option<String> } — the harness accepts any string. Adding validation would be a behaviour change, and behaviour is out of scope.

One list, in the other client

editors/vscode/src/tab.ts:69 EFFORT_LEVELS — seven levels, with its own caveat one line above: "the Responses enum; Chat is free-style".

Decision: one EFFORT_LEVELS const in settings.rs holding those seven, with a doc comment naming tab.ts:69 as its twin, and the reciprocal comment on the TS side. The duplication is real and named — the alternative, lifting the list into the kernel, would make the kernel own a presentation vocabulary it deliberately does not enforce.

And an off-list value is preserved, not clamped. A hand-set medium-high renders verbatim; the first arrow press moves to (none), with the new value visible in the row. A deliberate action with a visible result — never a silent rewrite of something the user typed.

8Two lies the panel would otherwise inherit

both are on screen today

(1) /effort high pushes Request::SetEffort and never writes Status.effort (app.rs:4252–:4261) — while the header prints model · effort from it (ui.rs:838). (2) Status.context_limit is seeded once at launch (main.rs:2017), so the gauge's denominator is stale after any /model switch — and the panel would render that stale number as a ReadOnly row.

Both are the same shape: a display field with no writer. The honest fix is to read the agent rather than to mirror the request, which means one new read verb on the wire:

Answered from agent.effort() (agent.rs:178), agent.llm() (agent.rs:471), PlanModeHandle::get() (hooks.rs:75) and limits::model_limit(...) (limits.rs:63) — and mid-run from the read-only side handle (actor.rs:530), which is what lets a --socket client show the server's model instead of its own startup seed. An older peer catches the unknown verb as Request::Unknown (#[serde(other)], protocol.rs:366) and answers Ack — which reads as "unavailable", never as a value.

8.1 What a row does mid-run — and a reversal

The harness accepts a settings mutation mid-run and applies it at the boundary: actor.rs:681–:691 sends Ack then deferred.push_back(Message::Tell { .. }) for SetModel | SetTitle | SetEffort | SetPlanMode. So all three Request rows are optimistic with a pending mark: the intended value goes into Status immediately and the row shows high · pending until a Settings reply confirms it, or until AgentStart (the boundary passed) or Error (it failed) clears the mark.

v1 said the opposite, and v1 was right for v1

v1 argued that /effort must not write Status optimistically: with no on-screen editor, showing a target before it took effect was the more deceptive option. With a panel, the user pressed Enter on a row they can see — a panel that does not echo its own keystroke reads as broken. The pending mark is what makes the echo honest, and it exists only because the Settings reply now exists to settle it.

Two alternatives were rejected. Refusing while running: a run can be long, and mid-run model/effort changes are the harness's explicitly supported path. Showing old truth until the boundary: it makes the panel feel dead, and the user cannot tell a slow apply from a dropped keystroke.

9What the panel refuses to claim

A "central setting" invites the belief that it is complete. It is not, and saying so is part of the design.

  • Provenance on any editable row. ProviderProvenance covers exactly four fields (config.rs:662–:668), and from inside the client a --model flag is indistinguishable from a /model override. So session rows carry values and durability only ("session — not persisted"), and provenance lives in the config section where the CLI already computed it.
  • Nine config tables with no TUI representation — [skills], [instructions], [retry], [compaction], [tools], [models.<id>] profiles, [peers], [workflow], [orchestrator]. The config section is exactly --dump-config's scope, and nothing more.
  • A tool-output value. Expansion is per block; the row carries the key (Ctrl-T) and says it has no default setting.
  • The server's config, over a socket. The section is labelled config (this client) because the server's config.toml is not on the wire. Only the session rows are server truth.
  • A typed field. No reusable single-line input exists — the composer is an app-level buffer with private edit methods (app.rs:2493–:2495, :4578), and the other two buffers are cursor-less Strings. So integers nudge and effort cycles; /width 96 and /effort high stay the escape hatches, unchanged.

11Proving it

Check (b) is the one that justifies §3: without the host decision, pressing Enter on the model row would close the editor — precisely the thing the ask modelled the whole panel on.

the traps the tests must pin

Two are compile errors, one is silent. ui.rs:235's match app.overlay() is exhaustive, and actor.rs:497 is the Request tail — a forgotten arm there does not build. But on_overlay_key is if matches! { … } plus _ => {} (app.rs:5149–:5175), so a variant routed there swallows every key with no compile error. The test must therefore assert positive movement — the cursor advanced, the value changed — not merely that the panel is open.

12The fork

awaiting sign-off · the only question that changes the plan

Does a change stick for the next launch?

No (this brief, all eight steps) — session-scoped, no writer. It is the D016-consistent reading, it is what "edit as model" describes (/model does not persist either), and it is the whole reason the panel is cheap.

Yes — a different, roughly twice-as-large item: this repository's first config.toml write path. A Serialize on FileConfig (today Deserialize only, config.rs:567), a target choice (global vs project overlay), merge-vs-replace against a partially hand-edited file, atomic write, per-row validation, its own record — and a subtlety that argues for keeping it separate: over --socket it would write the client's config while the agent lives on the server, so "stick" would not mean what the user expects.

orchestrator's read

Ship it session-scoped. The panel is worth having on its own terms, and persistence is the one part of it that puts a human's only hand-edited file at risk. Sequencing the two means the second can be refused without the first being wasted — and the getter, which is the genuinely reusable piece, lands in either case.

13Unverified

Named so nobody mistakes them for checked facts. Everything came from reading source; no build, test, clippy, or binary ran during recon or briefing.

  • Both staleness defects are code-inferred, not observed. No writer exists outside the two startup seeds — re-verified by grep — but nobody watched a header go stale.
  • ui.rs (~6000 lines) was not read end to end; another Status-derived readout is possible.
  • The exhaustive-vs-silent claim covers ui.rs:235, actor.rs:497 and app.rs:5149 — not every other match on Overlay/Mode/Request in the workspace, so a third silent site is possible.
  • editors/vscode/ was swept, not read: whether the extension already displays model/effort somewhere that would also be stale is unknown, as is whether adding a union member alone keeps npm test green.
  • Real-terminal F2 delivery is unverified — the same class of risk F1 already carries, and the reason /settings is a second door.
  • context_limit is None for most models today (limits::model_limit recognises one provider's catalogue), so the context row will usually read unknown and the gauge fix is invisible on a local model. An honest unknown still beats a stale number.
  • The omarchy theme label is undecided — it is a sentinel, not a catalogue entry, and nothing stores the active name today.
  • help_lists_…'s name list is already incomplete (it omits view) while its count is derived, so adding /settings will not fail it — which changes what that gate proves.
